# 커밋 · PR · 브랜치 이름

> 커밋은 **사용자가 요청할 때만** 합니다. 이 스킬은 "어떻게 쓸지" 이지 "언제 할지"가
> 아닙니다.

커밋 요약 줄 · PR 제목 · 브랜치 이름이 **같은 접두사 하나**를 공유합니다. 한 PR 에
한 가지 변경만 담으므로 접두사도 하나로 정해집니다.

```
<PREFIX>: <요약>

<본문 — "왜" 를 적습니다>
```

## 1. 무엇이 바뀌었는지 먼저 보세요

접두사는 diff 를 보고 정합니다. 기억이나 추측으로 붙이지 마세요.

```bash
git status --short
git diff --stat
git diff            # 스테이지 전
git diff --staged   # 스테이지 후
```

## 2. 접두사 하나 고르기

| 접두사 | 쓰는 때 | 예 |
| ------- | ---------------------------------------------- | ----------------------------------------------- |
| `ADD:`  | 없던 것을 새로 넣을 때 — 기능 · 엔드포인트 · 테스트 · 워크플로 · 의존성 추가 | `ADD: 환승 조회 엔드포인트` |
| `FIX:`  | 버그 수정 — 의도한 동작과 실제가 달랐던 것 | `FIX: 자정을 넘기는 열차의 도착 시각이 하루 밀리던 문제` |
| `REF:`  | 코드 구조 리팩터링 — **겉보기 동작은 그대로** | `REF: 폼 조립을 ApiClient.base_payload 로 통합` |
| `DEL:`  | 제거 — 기능 · 파일 · 죽은 코드 | `DEL: 쓰이지 않던 pay_with_card 별칭` |
| `DOCS:` | 문서만 — README · AGENTS.md · 독스트링 | `DOCS: 환승 조회 레퍼런스 추가` |
| `UPT:`  | 의존 패키지 **버전 업데이트** | `UPT: curl_cffi 0.16.3` |

대문자 + 콜론 + 공백 하나입니다. `Add:` 나 `ADD :` 가 아닙니다.

### 경계가 헷갈릴 때

이 여섯 개는 겹치는 지점이 있습니다. 아래 순서로 판단하세요.

**1. 겉보기 동작이 바뀌었나?**

- 바뀌지 않았다 → `REF:`. 리팩터링의 정의가 그것입니다.
- 새 동작이 생겼다 → `ADD:`
- 잘못돼 있던 동작을 바로잡았다 → `FIX:`

`REF:` 를 붙였는데 사용자가 체감할 변화가 있다면 접두사가 틀렸습니다.

**2. 코레일이 API 를 바꿔서 대응한 것은 `FIX:` 입니다.**

우리 코드가 잘못 짜여서가 아니라 서버가 움직여 더 이상 맞지 않게 된 것이지만,
결과적으로 "동작하지 않던 것을 동작하게" 만드는 일입니다. `external-api` 라벨을
함께 붙이세요.

**3. 의존성은 추가와 업데이트를 구분합니다.**

- `pyproject.toml` 에 새 패키지를 넣었다 → `ADD:`
- 이미 있던 패키지의 버전만 올렸다 → `UPT:`
- `uv.lock` 만 갱신됐다 → `UPT:`

**4. 문서와 코드를 같이 고쳤다면 `DOCS:` 가 아닙니다.**

`DOCS:` 는 **문서만** 바뀐 커밋입니다. 코드를 고치면서 그에 맞춰 문서를 갱신한
것은 주된 변경의 접두사(`ADD:` · `FIX:` · `REF:`)를 따릅니다.

**5. 테스트만 추가했다면 `ADD:` 입니다.**

없던 테스트를 넣는 것이니까요. 기존 테스트를 구조만 정리했다면 `REF:`.

**6. CI · 린트 설정은 무엇을 했느냐로 갈립니다.**

새 워크플로·규칙 추가 → `ADD:` / 구조 정리 → `REF:` / 제거 → `DEL:`

**7. 두 접두사가 다 어울린다면 커밋을 쪼개라는 신호입니다.**

"기능 추가하면서 김에 리팩터링" 은 두 커밋입니다.

## 3. 요약 줄

- **한국어 명사형 종결**, 마침표 없이 (`… 추가`, `… 통합`, `… 문제`, `… 제거`)
- 접두사 포함 50자 안팎
- 무엇이 바뀌었는지 한 줄로 — 파일 이름 나열이 아니라 **변화**를 적습니다

```
좋음:  FIX: 자정을 넘기는 열차의 도착 시각이 하루 밀리던 문제
나쁨:  FIX: schedule.py 수정
나쁨:  FIX: 버그 고침
```

## 4. 본문 — **왜**

`AGENTS.md` §4 의 "주석은 무엇이 아니라 왜" 와 같은 원칙입니다. **무엇**은 diff 가
이미 말하므로 본문에 적을 필요가 없습니다.

이 저장소에는 **이유 있는 이상한 코드**가 많습니다. 이유가 남아 있지 않으면 다음
사람(또는 다음 에이전트)이 "정리"하려 들고, 그게 조용한 회귀가 됩니다.

```
FIX: 과거 시각 조회를 요청 전에 차단

서버가 과거 시각에도 빈 결과만 주기 때문에 "떠난 열차"와 "열차 없음"이
구분되지 않았습니다. 사용자 쪽에서는 매진으로 오인하고 재시도 루프를
계속 도는 형태로 나타났습니다.
```

본문이 필요 없을 만큼 자명한 변경이면 요약 줄만 있어도 됩니다. 하지만 **외부 API
불변식**(`constants.py` · `auth/` · `crypto.py` · 폼 필드)을 건드렸다면 본문은
필수입니다 — 무엇을 근거로 그 값을 바꿨는지 적으세요.

## 5. 브랜치 이름

`<접두사 소문자>/<요약-kebab>`

```
add/transfer-endpoint
fix/midnight-arrival
ref/unify-ci-runners
del/legacy-pay-alias
docs/reference-transfer
upt/curl-cffi
```

## 6. PR 제목과 라벨

**제목은 커밋과 같습니다** — `FIX: 과거 시각 조회를 요청 전에 차단`.

`main` 은 squash 머지가 가능해서(`allowed_merge_methods` 에 `squash` 포함) PR 제목이
그대로 히스토리에 남습니다. 두 체계가 다르면 main 의 로그가 섞입니다.

접두사는 **변경의 종류**를, 라벨은 **릴리스 노트 분류**를 말합니다
(`.github/release.yml`).

| 접두사 | 라벨 | 릴리스 노트 |
| ------- | ------------------------------------------- | ----------- |
| `ADD:`  | `feature` | ✨ 새 기능 |
| `FIX:`  | `bug` | 🐛 버그 수정 |
| `REF:`  | `refactor` (CI·테스트만이면 `ci` · `test`) | 🧹 내부 정리 |
| `DEL:`  | `refactor`, 공개 API 를 없앴다면 `breaking` 추가 | 🧹 · 💥 |
| `DOCS:` | `documentation` | 📝 문서 |
| `UPT:`  | `dependencies` | 📦 의존성 |

**`security` 와 `external-api` 는 접두사가 없습니다.** 어느 접두사에나 덧붙는
직교 라벨입니다.

- 코레일 API 대응 → `FIX:` + `bug` + `external-api`
- 보안 수정 → `FIX:` + `bug` + `security`

## 7. 커밋 전 점검

- [ ] 접두사가 diff 와 맞습니까? (동작이 바뀌었는데 `REF:` 는 아닌지)
- [ ] 한 커밋에 한 종류만 담겼습니까?
- [ ] 요약 줄에 **변화**가 적혀 있습니까? (파일 이름 나열이 아니라)
- [ ] 이상해 보이는 코드에 **왜** 가 본문이나 주석에 남았습니까?
- [ ] 네 개 게이트를 통과했습니까? (`verify` 스킬)
- [ ] 자격증명 · 카드번호 · 실제 예약번호가 섞여 들어가지 않았습니까?
      (`a.py` · `scratch*.py` · `local/` 은 `.gitignore` 대상입니다)

## 8. 이 규약이 강제되지는 않습니다

CI 가 커밋 메시지 형식을 검사하지는 않습니다. 사람 기여자에게는
`CONTRIBUTING.md` 에 같은 내용이 안내로 적혀 있고, 형식이 틀렸다고 PR 을
돌려보내지 않습니다 — 메인테이너가 고칩니다.

에이전트는 지키세요. 히스토리를 읽는 비용이 곧 다음 작업의 비용입니다.
